# Handoff to Astra (Unity / Simulation Platform)

## Who you are and what you own

Astra (OpenAI ChatGPT Work) owns the Unity project and every Tier A simulation in Swoon'd (product spec sections 28-29, 50). Claude Code owns the native app (SwiftUI now, Compose later). The two sides meet only at the **bridge contract**: `docs/contracts/unity-bridge/v1/`. Do not change it unilaterally (spec section 31; DECISIONS D-010). Propose changes through a DECISIONS entry.

You own: Unity project architecture, the **Swoon Game Kit**, Unity C#, simulation systems, physics, procedural scenes, camera and input systems, game-state machines, reusable sport modules, asset integration, Unity tests, Play Mode verification, performance, iOS and Android Unity builds, and the Unity side of the bridge.

You do NOT own: navigation, profiles, progression (XP/hearts/streak/mastery application), paywall, notifications, lesson UI, native exercises, backend. Never build those inside Unity.

## Tools and versions (D-005)

- **Unity 6.3 LTS** (currently 6000.3.24f1). Do not adopt Mainline (6000.6.x) until it becomes LTS.
- **Universal Render Pipeline (URP)**, mobile settings. No HDRP.
- **Unity as a Library (UaaL)** for iOS (`UnityFramework`) and Android (`unityLibrary` AAR). The native app is the host; Unity is never the app.
- iOS build target: iOS 18.0 minimum, arm64, Metal. Android: later, same contracts.
- C# code-driven scene construction; data-driven sims (`docs/contracts/sim-definition/v1/`). Avoid hand-edited scenes; if a scene asset is unavoidable it must be generated by an editor script that is checked in.
- Tests: Unity Test Framework, **EditMode** (logic, schema, data) and **PlayMode** (scene + timing). CI-runnable headless where possible.

## How to read a sim spec

Every Tier A game is specified in `docs/courses/<course-id>/sims/<simulationId>.md` using `SIM_SPEC_TEMPLATE.md`. Read in this order:
1. **Sections 1-5:** identity/version, course links, learning objectives and concepts, why Unity, player fantasy and core loop.
2. **Sections 6-8:** scene and entities (Game Kit primitives), touch controls, flow state machine.
3. **Sections 9-11:** difficulty levels, configuration schema, scenario data set.
4. **Sections 12-15:** explain moments (the teaching copy), scoring and mastery mapping, XP/hearts, failure states.
5. **Sections 16-22:** accessibility, audio/haptics, assets, budgets, telemetry, acceptance criteria and test plan: your definition of done.

The spec is the contract; if it is ambiguous, list the question in your PR/hand-back and continue with the safest reading. Educational clarity beats realism (ART_DIRECTION.md).

## Deliverable expectations (per sim)

1. C# implementation built from Game Kit primitives (new primitives only when the spec justifies them and they are reusable).
2. Sim definition file(s) validating against `sim-definition.schema.json` where the sim is data-driven.
3. `configuration` JSON Schema fragment matching the spec (section 10 of the template) shipped alongside the sim.
4. Bridge conformance: reads every example in `docs/contracts/unity-bridge/v1/examples/`, emits `ready`, `progress`, `checkpoint`, one `result`, `requestExit`; result validates against `simulation-result.schema.json`.
5. EditMode + PlayMode tests covering every acceptance criterion in the spec.
6. Performance report against the budgets below on iPhone 13-class hardware.
7. Build artifacts: UaaL iOS framework + Addressables bundles (bundle layout in the bridge README section 5).
8. Changelog entry and the `simulationVersion` bumped per semver.

## Budgets (defaults; a sim spec may tighten, never loosen without approval)

| Budget | Value |
|---|---|
| Frame rate | 60 fps sustained on iPhone 13-class; 5th-percentile frame >= 50 fps; may drop to 30 fps only on Reduce-Motion-independent explicit "replay" sequences |
| Memory | < 150 MB total Unity resident memory during play (peak), returns to baseline on unload |
| Cold launch of a sim | < 2 s from `launch` received to `ready` (Unity library already loaded); < 4 s including first-time framework load |
| Per-sim download | <= 25 MB compressed Addressables bundle; core Game Kit + shared assets <= 40 MB in the app |
| Per-sim asset budget | Textures <= 8 MB VRAM total, meshes <= 60k triangles on screen, <= 15 materials, audio <= 3 MB |
| Draw calls | <= 150 on screen |
| Battery | A 3-minute session must not raise device thermal state above "fair" |
| Binary size | The Unity library adds <= 60 MB to the app thin download (track and report) |

## Conventions

- Namespaces: `Swoond.GameKit.*` (kit), `Swoond.Sports.<Sport>.*` (modules), `Swoond.Sims.<Course>.*` (sims), `Swoond.Bridge` (contract layer).
- IDs: `<simulationPrefix>.<topic>.<name>.v<N>` (e.g. `football.coverage.read.v1`).
- Determinism: every sim takes a seed (`configuration.seed`); with the same seed and inputs it plays out identically (needed for tests and replays).
- Theme: read colors/fonts from `LaunchRequest.theme`; never hard-code Swoon'd tokens.
- Accessibility flags from `learnerContext.accessibility` are mandatory: reduced motion, haptics, color-blind mode, text scale.
- Privacy: never log or transmit `personName`/`relationship`.
- Offline: no network calls.
